## 1. Why the next phase exists

D19-S8 established a production-safe, bounded, secretless empirical evidence surface for existing combo hard-gate outcomes without reevaluating gates or changing routing.

The original architecture calls for provider-neutral preference intelligence only **after** hard gates.

The next milestone should therefore investigate preference intelligence as a shadow/non-authoritative analysis layer before any routing authority is considered.

## 2. Phase objective

Design and qualify a deterministic provider-neutral preference-intelligence shadow that:

- sees only candidates that survived existing hard gates;
- uses bounded aggregate routing/outcome evidence rather than prompts, messages, raw responses, credentials, cookies, or session secrets;
- can compare surviving candidates using stable, explainable features;
- cannot re-admit or revive a hard-gate failure;
- cannot dispatch providers;
- cannot alter combo order, fallback, admission, Auth Keeper state, explicit pins, or workload isolation;
- produces evidence suitable for later offline evaluation.

This phase begins as **observer-only**.

## 3. Hard architecture constraints

The shadow must never become a second router.

Authority remains:

- OmniRoute: routing, orchestration, provider/model selection, fallback, dispatch;
- Auth Keeper: credential/session/account lifecycle and routing-safe eligibility/admission facts;
- Operations Floor: observer/operator plane;
- future preference component: recommendation evidence only until separately qualified and authorized.

Hard-gate facts outrank all preference signals.

A candidate with any existing terminal hard-gate rejection must remain ineligible regardless of preference score.

## 4. Minimum due diligence before implementation

Before creating source changes:

1. inventory the exact D19 bounded evidence schema and production tuple dimensions;
2. inventory existing OmniRoute scoring/ranking modules to avoid duplicating or competing with upstream architecture;
3. identify which existing signals are provider-neutral versus provider-specific;
4. identify any existing auto-combo scoring, speed ranking, cost, quota, reliability, session-affinity, or context-affinity layers;
5. distinguish hard eligibility from soft preference;
6. inspect current upstream release changes relevant to ranking/scoring/fallback;
7. define an offline deterministic evaluation dataset from bounded evidence;
8. define invariants proving that shadow evaluation cannot trigger provider/Auth Keeper requests;
9. define feature redaction/retention bounds;
10. define exact rollback/non-live qualification boundaries before any live authority experiment.

## 5. Initial feature classes to evaluate

Candidate feature classes may include, only where already available as bounded/aggregate facts:

- observed success/failure outcome frequencies;
- latency aggregates;
- recent cooldown/breaker health as already-computed eligibility context;
- quota headroom only after quota hard gates;
- context fit/headroom only after context hard gates;
- cost aggregates where policy allows;
- provider/model reliability aggregates;
- connection/session affinity as an existing routing fact, not a hidden identity signal;
- workload/capability match as a hard gate, never merely a preference feature.

Do not add prompt semantic content or user-sensitive payloads to make scoring richer.

## 6. Required shadow outputs

A first implementation should return only bounded analysis such as:

- candidate identifier in the same sanitized target vocabulary already approved for observability;
- hard-gate survivor status;
- normalized feature vector;
- deterministic shadow preference score or ordering;
- reason codes derived from bounded features;
- confidence/data-sufficiency indicator;
- disagreement with existing routing choice, if any.

The output must not be read back into live routing.

## 7. Qualification expectations

Before any authority consideration, require:

- deterministic fixed-fixture tests;
- invariant tests showing hard-gate failures cannot reappear;
- no provider request delta;
- no Auth Keeper request delta;
- no credential acquisition;
- no prompt/raw-response access;
- bounded serialized output;
- contained observer/scorer errors;
- baseline parity for existing routing;
- offline comparison against real D19 frozen evidence;
- explicit analysis of bias toward providers with more observations;
- cold-start behavior that does not manufacture confidence;
- no use of external benchmark rankings as routing authority.

## 12. Recommended first post-D19 implementation seam

The smallest architecture-preserving next step is **not** a new router and not a modification to `combo.ts`.

Recommended first implementation:

**D19-aware read-only preference shadow / scoring-inspector extension**

Properties:

1. lives in the observer/operator plane;
2. consumes frozen/bounded D19 aggregate evidence plus already-approved health/forecast/scoring inputs;
3. calls pure scoring/factor functions with injected data;
4. emits a deterministic recommendation/explanation only;
5. never feeds its result into `handleComboChat`, `orderTargetsByEvalScores`, auto-combo runtime selection, credential selection, or dispatch;
6. management-authenticated if exposed through an API;
7. includes explicit `authoritative=false` / shadow semantics in its contract;
8. records data sufficiency and avoids treating missing history as confidence;
9. does not use prompt/messages/raw response data;
10. does not create provider or Auth Keeper requests.

A first non-live qualification should compare:

- existing runtime order/choice;
- read-only existing scoring-inspector recompute;
- D19-aware shadow recommendation;

without allowing the shadow to change either runtime result.
