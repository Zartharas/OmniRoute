## 3. Current source behavior — important finding

The current request-compatibility design does **not** treat context-window mismatch like tools/vision/structured-output/output-token hard incompatibility.

In `open-sse/services/combo/comboStructure.ts`:

- `HARD_COMPAT_REASONS` contains:
  - `tools`
  - `vision`
  - `structured_output`
  - `output_tokens`
- `context_window` is deliberately excluded from that hard set.

The source comment states that context metadata is advisory:

- known-fitting targets should be ordered first;
- catalog-too-small targets remain available for runtime fallback;
- stale catalog metadata must not remove the only target that could accept the request.

The compatibility orderer therefore:

1. computes context compatibility for each target;
2. keeps context-only rejected targets in the pool;
3. when at least one target is known to fit, moves known-fitting targets ahead of known-too-small targets;
4. preserves strategy order when every target is context/output-only rejected.

This behavior was reinforced by #8944 regression tests that changed known-too-small context targets from **dropped** to **demoted**.

## 4. Whole-pool overflow behavior

`open-sse/services/combo/knownContextOverflow.ts` implements a separate hard preflight:

- it rejects early only when **every target** has a known context limit and every one is too small;
- any unknown target keeps the pool fail-open;
- native Codex Responses pools have an additional client-managed-context exception for all-Codex targets.

This means the correct behavior for a mixed pool is not automatically “remove Granite.” The exact metadata for both `ibm-mta-free-first` members matters.

## 5. Downstream effective-limit behavior

`tests/unit/chatcore-combo-context-limit-8378.test.ts` proves another important distinction:

- the effective context limit enforced in `handleChatCore` can differ from a naive per-target catalog lookup;
- combo-specific or connection/runtime-derived context limits can become authoritative later in the dispatch path.

That is directly relevant to the observed 128,000 limit.

A plausible class of explanation is therefore:

- combo compatibility ordering did not know Granite was too small (or did not know a sibling was definitely larger);
- later `handleChatCore` resolved/enforced an effective 128,000-token limit;
- the request then failed after target selection.

This is a hypothesis to verify, not yet the accepted root cause.

## 7. Constraints for any future fix

- do not change D19 observability;
- do not convert context metadata into a hard filter without proving that stale/unknown metadata cannot incorrectly remove viable targets;
- do not force fallback for a request that is globally invalid for every target;
- preserve explicit pins;
- preserve capability/tool/vision hard-gate behavior;
- preserve workload isolation and Auth Keeper boundaries;
- preserve upstream-compatible fallback semantics;
- add focused tests before live qualification.

## 9. Definition of done

This investigation is not complete until evidence establishes one of these categories:

- **EXPECTED_BEHAVIOR:** request is globally/contextually terminal under intended semantics;
- **METADATA_GAP:** pre-dispatch target context metadata is incomplete/stale relative to the effective runtime limit;
- **ORDERING_DEFECT:** a known-fitting target existed but the known-too-small target incorrectly remained ahead of it;
- **FALLBACK_CLASSIFICATION_DEFECT:** the first target's target-specific context failure should have advanced to a viable sibling but was treated as request-terminal;
- **OTHER:** evidence-supported alternative.

Only then should a code change be proposed.
